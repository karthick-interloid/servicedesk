# Folder Conventions

This template is meant to be forked into real projects, so the `src/` layout follows a deliberate convention rather than growing ad hoc. This doc explains what each folder is for, so anyone extending the template (including future-you) knows where new code belongs without guessing.

## Current layout

```
src/
  app/                     — routes (Next.js convention, fixed location)
  instrumentation.ts       — Next.js convention, fixed location — do not move
  instrumentation-client.ts — Next.js convention, fixed location — do not move
  config/
    site.ts                — static app config, e.g. siteConfig (no validation, just values)
    env.ts                 — validated environment variables (see note below)
  schemas/                  — empty (.gitkeep) — zod validation schemas: input that gets parsed and can throw (see the config/ vs schemas/ note below)
  lib/
    utils.ts                — generic, framework-agnostic utilities (currently: cn(), a Tailwind classname merger)
  components/
    ui/                     — primitive/design-system components (Button, Input, Dialog, ...). Managed by shadcn/ui (components.json) — add more with `npx shadcn add <component>`.
    shared/                 — empty (.gitkeep) — composed, reused-everywhere pieces (Header, Footer, Container, ...) — not primitives, not feature-specific
  context/                  — empty (.gitkeep) — React context providers used across the app (e.g. a theme provider)
  services/                 — empty (.gitkeep) — server-only integrations: DB client, third-party API clients. Not for client-callable code.
  store/                    — empty (.gitkeep) — global client-side state (e.g. Zustand/Jotai stores), added once a state library is actually adopted — see note below
  skeletons/
    home.tsx                — route-level loading skeleton paired with src/app/loading.tsx (loading.tsx stays a thin file at its required fixed location and just renders this). A single small loading placeholder for one component belongs in components/ui/skeleton.tsx instead — this folder is for larger, route-shaped composed skeletons, not primitives.
  types/                    — empty (.gitkeep) — plain TS types/interfaces with no runtime behavior
  hooks/                    — empty (.gitkeep) — shared custom React hooks used across features
  actions/                  — empty (.gitkeep) — cross-cutting `'use server'` actions not owned by one feature — see note below
  features/                 — empty (.gitkeep) — feature-scoped modules, see below
```

`components.json` (repo root) is shadcn/ui's config, generated by `npx shadcn init`. It points `utils`/`ui`/`hooks` aliases at `@/lib/utils`, `@/components/ui`, `@/hooks` respectively — keep those folders at their current paths, since shadcn's CLI writes new components assuming those exact locations.

## `store/` — added ahead of a real state library

`src/store/` is currently empty and no state-management library (Zustand, Jotai, etc.) is in `package.json` yet. It was scaffolded intentionally, ahead of the "add on real need" rule the rest of this doc otherwise follows, because client state is a near-certain future need for this project specifically. When you add the library, `src/store/<domain>.ts` (e.g. `cart.ts`, `ui.ts`) is where each store goes — one file per logical piece of state, not one giant store file.

## Why folders are empty with `.gitkeep`

Git doesn't track empty directories. A `.gitkeep` is a convention (not a Next.js or npm feature — just an empty placeholder file) to make an intentionally-empty folder show up in the repo and communicate "this is where X goes," even before the first real file exists. When you add the first real file to one of these folders, delete its `.gitkeep`.

## The `config/` vs `schemas/` distinction (and a known TODO)

- **`config/`** is for things that are just data — no validation, can't throw. `site.ts` is the clean example: a plain object built from already-validated env vars.
- **`schemas/`** is reserved for `zod` schemas — things that validate input and can throw. The folder now exists (empty, `.gitkeep`), scaffolded ahead of the first schema so the convention has a home. Each app-wide schema goes in its own file, e.g. `src/schemas/newsletter.ts`; feature-specific schemas colocate under `src/features/<feature>/schemas/` instead (see below).
- **Still-open TODO:** `env.ts` technically belongs in `schemas/`, not `config/`, since its whole job is `schema.parse(process.env)`. It sits in `config/env.ts` for historical reasons (it predates this distinction). Move it to `src/schemas/env.ts` the same session you add the first non-env `zod` schema, so the convention and the code agree from day one instead of drifting. It hasn't moved yet because the folder is still empty — no real schema has been added, only the placeholder.

## Where tests go

Tests live in a top-level `test/` folder (a sibling of `src/`, not inside it), mirroring the `src/` layout — `src/lib/utils.ts` is tested by `test/lib/utils.test.ts`, `src/app/page.tsx` by `test/app/page.test.tsx`. Playwright end-to-end specs are the exception: they sit together under `test/e2e/` and are excluded from the Vitest run. See [IMPLEMENTATION.md](./IMPLEMENTATION.md#14-testing--vitest--playwright) for the runner setup. Once features exist, prefer colocating a feature's tests with it (`src/features/<feature>/...`) if that reads better for your team — the mirrored `test/` tree is the default for shared, app-level code.

## Where feature-specific code goes (once a feature exists)

None of the folders above are `features/`-scoped — they're all for code shared across the whole app. Once the template gains its first real feature (auth, billing, etc.), that feature's own schemas/components/hooks should colocate under `src/features/<feature>/`, e.g.:

```
src/features/auth/
  schemas/
    login.ts
    signup.ts
  components/
  actions.ts
```

Don't add feature-specific files to `components/shared/`, `hooks/`, `types/`, `schemas/`, `context/`, `services/`, `store/`, `skeletons/`, or `actions/` — all of those stay reserved for things genuinely used across more than one feature. If something's only used by one feature, it belongs inside that feature's own folder, not in the shared ones.

## Server Actions (`'use server'` functions)

Two homes, split by ownership — same rule as everything else in this doc, not a special case:

- **Feature-owned** (the common case): colocate as `actions.ts` inside that feature, e.g. `src/features/auth/actions.ts` (login, signup, logout — nothing outside auth calls these).
- **Cross-cutting, not owned by one feature**: `src/actions/`. This is currently empty (`.gitkeep`) in the template itself — the template has no features yet, so there's nothing to be cross-cutting _between_. It's scaffolded now, ahead of real content, specifically for when this template is cloned into an actual application (same reasoning as `store/`): real apps tend to accumulate a handful of actions that don't belong to any single feature (e.g. a newsletter-signup action, a contact-form submit, an analytics-event log), and this is where those go once they exist.

Either way, the action itself should stay thin — the `'use server'` entry point invoked from a client component — and delegate the actual work to `services/` (the DB client, third-party API clients). Don't inline DB/API logic directly into an action file, feature-owned or not: `src/features/auth/actions.ts` calls `src/services/db.ts`, it doesn't reimplement it.
